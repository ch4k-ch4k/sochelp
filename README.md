# CTF SOC для команды

## Ограниченный Интернет и продолжение после ошибок

```bash
sudo bash install.sh --get-only
sudo soc install-report
```

`--get-only` использует APT HTTP(S)-загрузки GET и **пропускает Git, Docker pull/build и настройку командного сервера**. Веб-комплект этим режимом не устанавливается; уже существующий командный сервер не пересоздаётся. `--pro --get-only` также пропускает веб-компоненты. HTTPS через HTTP proxy дополнительно требует CONNECT; если организаторы разрешают только GET без TLS-туннелей, HTTPS-репозитории могут быть недоступны. Ограничения сайтов, CA и системные APT hooks остаются настройками окружения. Этот режим не превращает Docker Registry и Git в протоколы только с GET.

В обоих режимах каждый APT-пакет устанавливается отдельно. Установленные пакеты пропускаются, а ошибка одного пакета не отменяет остальные попытки. APT может менять зависимости для установки новых пакетов: это не транзакционная установка и не гарантия отсутствия любых изменений системы. Резервные копии ранее установленной команды `soc`, helper и справки сохраняются в `install-*.previous`. Перед обычной перенастройкой сервера создаются копии его конфигураций `team-config-before-*`.

Если не работает Docker Compose, серверный этап пропускается. Ошибка зависимого этапа прерывает этот этап; независимые последующие загрузки образов WAF/Firegex всё равно пробуются. База Packmate и каталоги данных при сбое не удаляются. Это не означает, что каждый веб-компонент обязательно установится независимо от остальных: у них общие зависимости и этап конфигурации.

Отчёт `install-*.report.tsv` содержит `OK`, `FAILED`, `SKIPPED`; последнюю версию показывает `sudo soc install-report`. После частичной установки с ошибками скрипт возвращает код **2**, уже после остальных попыток. Ошибки прав, блокировки установщика, неподдерживаемая ОС, чужой `/usr/local/bin/soc` и неверные/конфликтующие параметры могут остановить работу раньше. Для повторной попытки устрани причину из лога и запусти установщик заново. Полный профиль запускай без `--get-only`, когда есть подходящий доступ к сети.

Один автономный `install.sh` для **Ubuntu Server 26.04 LTS (amd64)**, также поддерживает Ubuntu 22.04 / 24.04 и Kali Linux rolling. По умолчанию устанавливает общий Packmate, инструменты анализа трафика и хоста, Suricata и команду `soc`. Тиммейты открывают один веб-интерфейс и работают с общей базой потоков, сервисов и паттернов.

Для Ubuntu 26.04 (Resolute) проверено наличие всех 53 запрошенных имён пакетов в индексах amd64 `main`/`universe`. Установщик принимает `VERSION_ID=26.04` и использует пакеты Ubuntu. CLI-профиль и командные компоненты проверялись в настоящей VM Ubuntu 26.04 ARM64; полный непрерывный прогон на нативном amd64 пока не подтверждён.

Результаты живой проверки 20.11.2026 записаны в [VERIFICATION.md](VERIFICATION.md): CLI-профиль установлен на Ubuntu 26.04 ARM64, проверены реальный PCAP, Suricata, выкладка/откат и работа HTTP WAF. Полный amd64-профиль требует отдельной оценки, указанные проверки его целиком не подтверждают. В результате проверки исправлено имя APT-пакета: `bind9-dnsutils` вместо отсутствующего в 26.04 `dnsutils`.

Также исправлены временные каталоги read-only Nginx, сборка PostgreSQL-расширений Tulip при несовпадении LLVM и конфликт Basic/Bearer авторизации Firegex. После исправлений живые HTTP-проверки портала, бинарной загрузки, CyberChef, Tulip (включая приём PCAP) и Firegex прошли. Packmate подтверждён в VIEW; его LIVE-захват на нативном amd64 ещё требует проверки. Импорт в Tulip асинхронный: поток может появиться через несколько десятков секунд после чтения PCAP.

В Kali используется `docker.io` и пакет **`docker-compose` версии 2** из репозитория Kali, в Ubuntu — `docker-compose-v2`. Buildx, OpenSSH, инструменты архивирования и остальные зависимости ставятся установщиком. Проверяется `ID=kali`, версия rolling не сравнивается с номерами Ubuntu. Пакеты берутся из уже настроенных репозиториев; смешивать Kali с репозиториями Ubuntu не нужно. Установка OpenSSH не меняет ключи или парольную политику и не гарантирует автоматический запуск SSH-службы.

## Настройки по фотографиям игры

Из пяти фотографий перенесены известные адреса и порядок старта. В **новой** конфигурации Tulip тик задан в 120 000 ms и lifetime в 5 тиков. Существующий `.env` сохраняется: при обновлении проверь `TICK_LENGTH=120000` и `FLAG_LIFETIME=5` в `/opt/ctf-soc/tulip/.env`, затем выполни `sudo soc pro up`. Начало игры и формат флага на фото не указаны — их нужно уточнить у организаторов.

```bash
soc endpoints           # Все адреса со слайдов и собственные маршруты SOC
soc tutorial full       # SSH, инвентаризация, резервные копии и ограничения proxy
sudo soc inventory      # Сервисы, TCP/UDP, контейнеры, firewall на текущем хосте
```

Список адресов также доступен на `http://SERVER:65002/endpoints.txt` и по карточке портала. [ENDPOINTS.md](ENDPOINTS.md) содержит таблицы и пояснения. Порты игровых заданий на фотографиях отсутствуют; установщик не угадывает их. Автоматическое закрытие портов и удаление SSH-ключей не выполняются: сначала нужно проверить игровой доступ и сохранить возможность входа.

**Для полного SOC + DevOps набора запускай профиль PRO:**

```bash
sudo bash install.sh --pro --interface eth0 --local-ip 10.10.1.2 --services web:8080,pwn:31337
```

Он также устанавливает зависимости сборки Docker, собирает Tulip, скачивает CyberChef, Nginx, Python, Firegex и OWASP ModSecurity CRS, поднимает командный портал с загрузкой артефактов. Firegex и отдельные WAF-прокси запускаются командами оператора. Только `install.sh` нужен для установки; все конфигурации и вспомогательные программы он создаёт сам.

Подробный [туториал SOC/DevOps на A/D CTF](PLAYBOOK.md) содержит настройку WAF, работу с чекерами, загрузку бинарников и Python-релизов, health checks и откат.

**Туториал встроен в установщик и доступен на самом сервере без компьютера автора:**

```bash
soc tutorial          # Коротко: как работать и загружать исправления
soc tutorial full     # Полный встроенный туториал, без sudo и Интернета
```

В PRO открой **`http://SERVER:65002/tutorial.html`** или карточку «Как всем пользоваться» на портале. Там же можно скачать текстовую памятку. Логин такой же, как у портала. Установщик сам создаёт `/usr/local/share/ctf-soc/TUTORIAL.txt` и веб-страницу; копировать `PLAYBOOK.md` на Ubuntu отдельно не требуется. Для добавления справки к уже установленному набору повторно запусти обновлённый `install.sh` с тем же профилем.

| Адрес PRO | Назначение |
| --- | --- |
| `http://SERVER:65002` | Общая стартовая страница, скачивание файлов, загрузка любых артефактов до 100 MB |
| `http://SERVER:65000` | Packmate |
| `http://SERVER:65003` | Локальный CyberChef |
| `http://SERVER:65004` | Tulip |
| `http://SERVER:65005` | Firegex после `sudo soc firegex up` |

Портал, CyberChef и Tulip используют общий Basic Auth из Packmate. Firegex использует собственный пароль/JWT, заданный при первом запуске в терминале; дополнительный Basic Auth на порту 65005 выключен, поскольку он конфликтует с Bearer-токенами API. Внутренние порты 65103/65104/65106 и Firegex:4444 привязаны к localhost. Веб-интерфейсы рассчитаны на командную VPN/LAN; сервер WAF для игровых запросов не требует логина команды.

## Почему эти инструменты

Вместо неподтверждённого рейтинга «топ тим» использованы первичные источники:

- [Tulip](https://github.com/OpenAttackDefenseTools/tulip) прямо указывает разработку **Team Europe** для International Cyber Security Challenge: совместные ссылки на потоки, diff, генерация Python-сниппетов.
- [Icegex](https://github.com/ECSC-Team-Poland/icegex) — firewall **ECSC Team Poland**, форк Firegex. В набор включён его upstream [Firegex](https://github.com/Pwnzer0tt1/firegex), для которого доступны готовый образ и документация фильтров. Icegex изучен как командная альтернатива, одновременно второй firewall не устанавливается.
- [Packmate](https://gitlab.com/packmate/Packmate) специализируется на перехвате и анализе трафика CTF.
- [OWASP CRS](https://github.com/coreruleset/modsecurity-crs-docker) — поддерживаемый набор общих HTTP WAF-правил. Это дополнение для web-сервисов; для бинарных TCP/UDP-протоколов используются патчи и Firegex.
- [CyberChef](https://github.com/gchq/CyberChef) выполняет преобразования данных в браузере, включая работу в закрытой командной сети после скачивания образа.

Факт публичного использования одного инструмента конкретной командой не означает, что весь этот комплект используется ею целиком.

## Выкладка исправлений

На портале загрузи готовый ELF, `.py`, конфиг или `.tar.gz`. Полученный путь передай администратору. Для SSH можно использовать `scp` в `/srv/ctf-soc/shared`.

```bash
# Готовый бинарник: заменить server, сохранить существующий executable mode.
sudo soc deploy stage /srv/game/pwn /srv/ctf-soc/shared/server.fixed \
  --target server --restart-systemd game-pwn.service --tcp 127.0.0.1:31337

# Отдельный Python-файл.
sudo soc deploy stage /srv/game/web /srv/ctf-soc/shared/app.fixed.py \
  --target app.py --restart-container game-web --health http://127.0.0.1:8080/health

# Несколько файлов сервиса: пути в tar.gz отсчитываются от /srv/game/web.
sudo soc deploy stage /srv/game/web /srv/ctf-soc/shared/release.tar.gz \
  --restart-systemd game-web.service --health http://127.0.0.1:8080/health

sudo soc deploy show ID
sudo soc deploy apply ID
sudo soc deploy rollback ID
sudo soc deploy list
```

`ID` напечатает `stage`. Веб-загрузка сохраняет артефакт, применение выполняет администратор через CLI. Для нового бинарника укажи `--mode 0755`; у существующего файла по умолчанию сохраняются права. Архив сохраняет обычные Unix mode bits; symlink, hardlink, устройства и выход за каталог сервиса отклоняются. Лимит артефакта — 100 MB, архива — 1 GB после распаковки и 10 000 записей.

Перед применением команда сверяет SHA-256, права и владельца затрагиваемых файлов, делает копии и записывает состояние. При ошибке рестарта или HTTP/TCP-проверки восстанавливает прежние файлы и повторяет рестарт. Проверка делает до пяти попыток. TCP-проверка подтверждает доступность порта; корректность игрового протокола проверяйте своим клиентом и чекером.

Релиз накладывается на каталог: он меняет перечисленные файлы, новые добавляет, не удаляет остальные. Рабочую БД и флаги не включайте в архив. Для diff-патчей есть `soc patch stage DIR FILE.patch` с теми же опциями рестарта и проверки. Автоматического `pip install`, миграций БД, сборки Docker-образа приложения или исполнения post-install hooks при выкладке нет; такие шаги определяются конкретным сервисом и описаны в туториале.

Отдельный файл заменяется атомарным rename; весь каталог целиком атомарно не переключается. В многофайловом сервисе возможен промежуточный набор версий до рестарта. Последующие правки другого участника блокируют применение/откат вместо перезаписи. Прерывание процесса в состоянии `applying` требует проверки журнала и ручного восстановления из `backup/`; автоматический откат не гарантируется при отключении питания или SIGKILL. Копии и история находятся в `/var/log/ctf-soc/patches`.

## Tulip и WAF

```bash
sudo soc pro status
sudo soc tulip-capture eth0 'tcp port 8080 or tcp port 31337'
# Либо импорт завершённого дампа:
sudo soc tulip-import ./traffic.pcap

# HTTP WAF на свободном тестовом порту:
sudo soc waf add web 18080 http://127.0.0.1:8080
sudo soc waf logs web
sudo soc waf mode web block
# Вернуть наблюдение без блокировки:
sudo soc waf mode web detect
```

Для PRO ориентируйся на **8 vCPU, 16 GB RAM и 80+ GB диска**, особенно если Tulip, Packmate и игровые сервисы работают вместе. Это стартовый ориентир, не гарантия на любую нагрузку. Сборка Tulip скачивает Go/Node/Python-зависимости внутри Docker и может занять заметное время. Обновляемые теги образов требуют Интернета при первой установке.

Tulip закреплён на `523e5179043a5b6ae1bbcc1990d774f23166319b`, Firegex — на `cfeed62d133e1dc418d452cc70ec953ec7806754`. Флаговый regex и параметры тиков настрой в `/opt/ctf-soc/tulip/.env`, список сервисов — в `services/api/configurations.py`; затем пересобери API через Docker Compose. Сборка профиля PRO не настраивает универсальную интеграцию всех логов Suricata с Tulip. PCAP-кольцо ограничено примерно 6 GB за один запуск захвата; база Tulip автоматически по размеру не ограничивается.

Каждый WAF работает отдельным Compose-проектом, сначала в `DetectionOnly`, с CRS paranoia level 1. Ответы сервиса WAF не анализирует; ограничения методов расширены до распространённых REST-методов. Журналы контейнера ротируются. `soc waf add` поддерживает HTTP backend на loopback и порт WAF 1024–65535. Его собственная health-проверка проверяет прокси, отдельно проверяй backend и игровые операции. Простое наличие WAF рядом с сервисом не направляет через него игровой трафик: настройка размещения показана в туториале.

## Запуск

Скопируй **только `install.sh`** на Kali/Ubuntu amd64, где проходит игровой трафик:

```bash
sudo bash install.sh
```

Установщик покажет интерфейсы и спросит игровой интерфейс и IPv4 вулнбокса. Эти данные можно сразу передать аргументами:

```bash
sudo bash install.sh --interface eth0 --local-ip 10.10.1.2
```

Замени `eth0` и `10.10.1.2` на реальные значения из `ip -br -4 address`. IP должен находиться на выбранном интерфейсе этого Ubuntu-хоста. Для простой установки Packmate запускается на самом вулнбоксе; отдельный SOC-сервер требует заранее настроенной доставки трафика и другой конфигурации захвата. Обычное подключение сервера к той же сети не даёт ему видеть трафик вулнбокса.

Нужны sudo, Интернет и штатные репозитории Kali rolling; для Ubuntu — `main`, `universe`, `updates`. Для командного сервера разумная стартовая конфигурация — 4 vCPU, 8 GB RAM и 40+ GB свободного диска; фактические требования зависят от трафика. Docker устанавливается из репозитория вашей ОС, если его ещё нет. Его запуск может повлиять на сетевые правила хоста — лучше развернуть набор до старта раунда. Прокси со слайдов разрешает только GET и ограниченные сайты, что может помешать установке и Docker Registry: готовьте образы и зависимости заранее либо согласуйте доступ с организаторами. Скрипт не импортирует неизвестный CA автоматически и не отключает TLS-проверку.

## Доступ команды

После установки:

```bash
sudo soc team credentials
```

Передай тиммейтам адрес **`http://IP_СЕРВЕРА:65000`**, логин `team` и сгенерированный пароль. Веб-доступ не требует SSH или установки инструментов на компьютеры тиммейтов. Это общий аккаунт Packmate, отдельные роли пользователей установщик не добавляет. Используйте командную VPN или доверенную LAN: стандартный Packmate передаёт Basic Auth по HTTP. Для доступа через SSH-туннель:

```bash
ssh -N -L 65000:127.0.0.1:65000 user@IP_СЕРВЕРА
# Затем открыть http://127.0.0.1:65000
```

Packmate слушает порт 65000 на интерфейсах хоста. Доступ из командной сети должен разрешаться существующим firewall; установщик не добавляет разрешающие правила. База PostgreSQL слушает только `127.0.0.1:65001`.

При первом входе:

1. Нажми `+` в верхней панели и добавь название и порт каждого игрового сервиса. **Пока сервисы не созданы, Packmate не сохраняет их потоки.** Для нескольких портов создай отдельные записи.
2. Для HTTP включи URL decode, merge adjacent packets и при необходимости chunked decoding.
3. В `Patterns` создай Highlight-паттерны под формат флагов игры, отдельно для запросов и ответов. Для поиска по уже сохранённым потокам используй Lookback.
4. Разделите сервисы между участниками. Сервисы и паттерны общие; каждый участник может просматривать потоки в своём браузере.

Данные переживают перезапуск контейнеров и `soc team down`. Автоочистка старых потоков включена с порогом **240 минут** и проверкой раз в минуту; это ограничение по возрасту, а не жёсткий лимит размера базы. Параметры находятся в `/opt/ctf-soc/packmate/.env`.

## Управление

| Команда | Что делает |
| --- | --- |
| `sudo soc team status` | Состояние контейнеров |
| `sudo soc team logs` | Общие логи в реальном времени |
| `sudo soc team down` | Остановить Packmate, сохранить данные |
| `sudo soc team up` | Запустить и дождаться готовности контейнеров |
| `sudo soc team credentials` | Посмотреть логин и пароль |
| `soc doctor` | Проверить наличие инструментов и IDS-правил |
| `sudo soc status` | Процессы, слушающие порты, соединения, сервисы |
| `sudo soc snapshot` | Сохранить состояние хоста и до 10 000 последних записей journal за 30 минут |
| `sudo soc capture eth0 'tcp port 8080'` | Кольцевой PCAP: 20 файлов примерно по 50 MB |
| `sudo soc rules-update` | Скачать правила Suricata и проверить конфигурацию |
| `sudo soc ids-pcap /path/traffic.pcap` | Разобрать PCAP через Suricata |
| `sudo soc ids-live eth0` | Запустить пассивную IDS до Ctrl+C |
| `sudo soc alerts /path/eve.json` | Смотреть алерты Suricata |
| `soc watch /path/service` | Следить за изменениями файлов |

Suricata здесь работает как пассивная IDS. Установщик не переводит её в IPS и не добавляет блокировки. Правила скачиваются отдельной командой, поскольку для них нужен доступ к внешнему источнику. В `ids-pcap` и `ids-live` обе стороны сети заданы как `any`, чтобы обработать произвольную адресацию CTF; это может увеличить число ложных срабатываний. Для точной настройки запускай Suricata напрямую с подходящим HOME_NET.

## Общие файлы и инструменты по SSH

Для работы в терминале тиммейт входит на Ubuntu по своему существующему SSH-аккаунту. CLI-инструменты установлены системно, а доступ к общей папке выдаётся так:

```bash
sudo soc member alice
sudo soc member bob
```

После нового входа эти пользователи могут читать и менять файлы в `/srv/ctf-soc/shared`. Участник, запустивший установку через sudo, добавляется автоматически. SSH-аккаунты и ключи администратор создаёт обычным способом. Членство в группе `ctf-soc` даёт доступ к общей папке; захват трафика и управление Docker требуют sudo.

```bash
soc publish ./interesting.pcap
# Получится отдельная share-XXXXXXXX/ с исходным именем файла.

# Администратор может поделиться результатом из закрытой папки:
sudo soc publish /var/log/ctf-soc/snapshot-.../host.txt

# Скачать на ноутбук (подставь путь, выведенный publish):
scp alice@IP_СЕРВЕРА:/srv/ctf-soc/shared/share-XXXXXXXX/interesting.pcap .
```

Захваты, снимки хоста и установочные логи находятся в `/var/log/ctf-soc`, доступной только root. Делись нужными файлами через `soc publish`. Ограничение кольцевого захвата действует отдельно на каждый запуск; предыдущие каталоги не удаляются автоматически.

## Опции и повторный запуск

```bash
bash install.sh --dry-run                         # План, без изменений
sudo bash install.sh --no-packmate                # Только инструменты и soc, без Docker
sudo bash install.sh --no-packmate --minimal      # Также без Suricata
sudo bash install.sh --with-auditd                # Дополнительно системный аудит
sudo systemctl enable --now auditd               # Включить аудит явно
```

Для `--with-auditd` при первой установке также нужны игровые интерфейс/IP или интерактивный ввод. Auditd устанавливается с настройками Ubuntu; собственные audit-правила набор не создаёт. Политика установки временно запрещает автоматический запуск сервисов пакетов, если на хосте ещё нет собственной `policy-rc.d`. Уже существующая политика администратора сохраняется. Новый сервис Suricata отключается; ранее установленный сервис сохраняет своё состояние. Автозапуск auditd при загрузке зависит от настроек пакета.

Повторная установка сохраняет `.env` и базу Packmate; значения `--interface` и `--local-ip` на повторном запуске не меняют существующую конфигурацию. Для смены параметров отредактируй `.env` через sudo и выполни `sudo soc team up`. Общие каталоги сохраняются. Управляемая команда `soc` обновляется, а чужой файл `/usr/local/bin/soc` установщик откажется перезаписывать.

Стартер Packmate закреплён на коммите `25a2517dceb567a1571cd3666cfaadee0b66779b`. Образ Packmate использует upstream-тег `latest`, поэтому повторная установка с `pull` может обновить его. ID скачанных образов записываются в `/opt/ctf-soc/packmate/installed-images.txt`; для фиксации версии перед раундом можно указать поддерживаемый upstream `BUILD_TAG` в `.env`. Не меняй `PACKMATE_DB_PASSWORD` у уже созданной БД без отдельной смены пароля в PostgreSQL.

Если Packmate не поднялся, проверь `sudo soc team logs`, занятость портов 65000/65001, доступ к registry.gitlab.com и свободный диск. Если APT не находит пакеты, проверь наличие `universe` и `updates`. TLS-трафик с современным ECDHE/TLS 1.3 не станет открытым текстом автоматически; возможности RSA-дешифрования описаны в [документации Packmate](https://gitlab.com/packmate/Packmate/-/blob/master/docs/SETUP.md).
